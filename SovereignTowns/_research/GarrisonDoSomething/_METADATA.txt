============================================
KEY OBSERVATIONS
============================================
A. NO HourlyTickSettlement / DailyTickSettlement usage. GDS subscribes ONLY to TickEvent
   and gates with `CampaignTime.Now` delta >= AttackInterval. This is a continuous-time
   self-paced check, much finer-grained than the IG approach.

B. NO custom PartyComponent — uses stock LordPartyComponent + a Harmony PREFIX patch on
   LordPartyComponent_InitializationArgs.InitializeLordPartyProperties to inject custom
   roster/owner/home. (IG by contrast subclasses WarPartyComponent — cleaner.)

C. Cleanup uses DestroyPartyAction.Apply (immediate object teardown), NOT
   DisbandPartyAction.StartDisband (which would walk the party home with disbanding behavior).
   This is paired with the WarPartyComponentPatch.OnFinalizePrefix to handle the moment of destruction.

D. Combat is AI-driven: SetMoveEngageParty + SetInitiative + SetDoNotMakeNewDecisions.
   No manual EncounterManager.StartPartyEncounter calls — the vanilla map-collision system runs the fight.

E. Spatial enemy search uses MobileParty.StartFindingLocatablesAroundPosition + FindNextLocatable
   (radius = MySettings.AttackDistance). NOT iteration of MobileParty.All.

F. No Mission / MissionBehavior / MissionLogic types referenced. Campaign-map only.
   FULLY ORTHOGONAL to RBM.

G. Wage zeroing (MobilePartyPatch.get_TotalWagePrefix) and clan-lock
   (MobilePartyPatch.set_ActualClanPrefix) are quality-of-life patches we can SKIP if we
   accept short-lived sortie parties (life ~AttackInterval hours, never a payroll tick).
